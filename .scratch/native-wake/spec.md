# 第一期：自定义唤醒词唤起原生小爱

Status: ready-for-agent
Execution: server-validated; offline-device-preparation-done; device-installed; core-acceptance-passed; playback-and-baseline-cases-pending
Scope: 仅改变唤醒入口，保留原生业务处理；设备安装尚未开始。

## Problem Statement

用户第一期只希望用自定义唤醒词唤起小米小爱音箱 Pro LX06，后续识别、回答、音色、米家控制、闹钟、提醒、红外和音乐均继续使用设备已有原生能力，不接入自定义 Agent。

## Solution

复用固定版本 Open-XiaoAI Bridge 的关键词检测和原生唤醒方法，以及音箱端 Rust Client。用户已确认新增唤醒词为“理想同学”，保留原厂“小爱同学”。默认交互为先说唤醒词，等原生反馈后再说指令；不承诺一句话同时完成唤醒和指令传递。服务器阶段先用合成语音和假 Client 静默验证，不播放声音；真人录音和真机声学验收后续补充。

## User Stories

1. 作为用户，我希望通过自定义词唤起原生小爱，以使用自己选择的称呼。
2. 作为用户，我希望唤醒后仍是原来的小爱，以继续使用已有技能和音色。
3. 作为用户，我希望获得原生唤醒反馈，以知道何时开始说指令。
4. 作为用户，我希望原厂词继续可用，以保留原有入口。
5. 作为用户，我希望多次唤醒都有效，以便日常使用。
6. 作为用户，我希望播报或音乐中的唤醒有明确测试结果，以了解打断能力。
7. 作为用户，我希望服务停机时原厂词仍可用，以保持基本功能。
8. 作为维护者，我希望检测服务不连接 Agent、模型或 HA，以缩小一期部署范围。
9. 作为维护者，我希望软件验证与真机唤醒分开记录，以避免过早声称成功。
10. 作为设备所有者，我希望安装前确认固件和恢复步骤，以保护设备。

## Implementation Decisions

- 在服务器侧做关键词检测，音箱 Client 提供音频和设备指令通道。用户已确认使用现有 Docker 服务器，不使用 PVE；已在 iStoreOS x86_64 / Docker 27.3.1 验证，真机经 `192.168.1.2:4399` 接入。
- 识别到自定义关键词后，只调用已有原生唤醒能力，把后续指令交回原生流程。调用返回成功不代替用户听到唤醒反馈和原生完成指令的证据。
- 将关键词检测启动、关键词模型准备与外部 AI 后端开关解耦；所有外部后端保持关闭，不通过虚假启用后端来启动检测。
- 配置必要的关键词/VAD 模型；不为一期安装本地全文 ASR 模型或自定义 TTS。
- 关闭或绕开 Bridge 对原生命令的外部唤醒词拦截、示例召唤转发和连续对话增强，避免改变原生业务行为。
- 加入必要的重复触发抑制，并实测播报回声，避免一次唤醒触发多个原生会话。
- 不替换原厂关键词模型；彻底禁用“小爱同学”是另一个需求，不视为已解决。
- 沿 Client 路线仍需核验 SSH/补丁固件兼容，软件方案不等于免刷机。

## Testing Decisions

- 使用假的音箱接口，验证关键词触发只调用原生唤醒，原生指令不转发到外部后端；覆盖重复触发和唤醒调用失败。
- 在全部外部后端关闭时验证关键词模型准备与检测启动，不触发模型服务连接。
- 真机验证自定义词唤醒→反馈→天气/安全设备控制/闹钟或计时器/音乐，分别记录原生功能。
- 验证连续多次唤醒、原厂词、播放中唤醒、Client/Bridge 断线和服务重启。先记录成功率、误唤醒及延时基线，不虚构目标。

## Out of Scope

自定义 Agent、OpenClaw、大模型、HA 工具、自定义 TTS、NAS 曲库、完整连续对话增强、彻底禁用原厂词，以及“唤醒词+指令”一口气说完的承诺。原生能力本身的局限继续存在。
