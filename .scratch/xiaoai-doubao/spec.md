# 小爱豆包：Hermes 对话、原生指令与动态语音

Status: ready-for-agent
Design: confirmed-product-boundaries; implementation-contracts-to-verify
Execution: ticket-01-mock-validated; tickets-02-through-07-pending; real-hermes-pending; silent-tests-only; production-unchanged

## Problem Statement

用户希望在保留“理想同学”和原厂“小爱同学”原生入口的同时，通过“豆包豆包”与 Hermes 助手聊天。普通聊天自然播报，操作请求优先调用原生小爱，并由发起请求的助手反馈结果。单纯的文字播放 skill 不足以覆盖原生指令、结果记录、对话协调与动态语音需求。

当前原生唤醒模式禁止外部 Agent 和 HTTP API，外部对话又会暂停自定义关键词检测；原生命令、Hermes 回复和音乐会争用同一音箱。需要沿用现有 Bridge 架构完成混合路由、工具封装与播报协调，并区分请求受理与操作完成。

实施期间宝宝正在睡觉。用户明确要求不触发真实音箱声音；开发和服务器测试必须与真实设备及生产服务隔离。

## Solution

新增“小爱豆包”，Hermes profile 为 `xiaoai-doubao`，唤醒词为“豆包豆包”，使用一个亲切、自然、简洁的默认人格和一个默认会话。同一个 Bridge 按唤醒词路由，原生入口继续使用原生能力，豆包入口使用 Hermes。

普通回复由 Bridge 自动合成播放，默认音色为豆包 Vivi 2.0。Hermes 根据当前 session 上下文动态判断情绪、语种、方言与阶段偏好，用户明确要求优先。原生指令和播放控制统一由本项目的 `xiaoai-bridge` skill 提供，替代独立的 `xiaoai-tts` skill 入口，暂不直接接 HA。

先交付可在独立服务器环境验证的静默闭环：文字或文件音频输入、Hermes 回复、声音要求、假音箱操作、持久化操作记录和音频文件输出。真实设备声学及原生业务验收另行等待用户允许。

## User Stories

1. 作为使用者，我希望说“豆包豆包”进入小爱豆包，以便与 Hermes 聊天。
2. 作为使用者，我希望“理想同学”和“小爱同学”继续进入原生小爱，以保留已有入口。
3. 作为使用者，我希望普通回复自动播报，以免每句话都要求调用播放工具。
4. 作为使用者，我希望默认听到 Vivi 2.0，以保持小爱豆包的统一声线。
5. 作为使用者，我希望回复带有合适的情绪，以使对话自然。
6. 作为使用者，我希望模型根据上下文判断语种和方言，以减少手动切换。
7. 作为使用者，我希望明确指定语气、语种或方言时得到优先遵循，以控制当前表达。
8. 作为使用者，我希望“这句用英语”只覆盖当句，以免破坏此前阶段偏好。
9. 作为使用者，我希望模型根据 session 记忆判断阶段偏好是否继续生效，以避免每次重新唤醒后重复设置。
10. 作为使用者，我希望不把阶段偏好保存为长期用户画像，以限制首版范围。
11. 作为使用者，我希望再次唤醒时延续默认会话，以便继续之前的话题。
12. 作为使用者，我希望服务重启后恢复默认会话，以免已有聊天上下文意外丢失。
13. 作为使用者，我希望能明确开启新会话，以清除旧上下文和旧声音偏好。
14. 作为使用者，我希望豆包把操作优先交给原生小爱，以复用已有的小米能力。
15. 作为使用者，我希望通过豆包发起的操作由 Hermes 用 Vivi 反馈，以保持助手一致。
16. 作为使用者，我希望从原生入口发起的操作继续由原生小爱反馈，以保持原有使用方式。
17. 作为使用者，我希望请求受理、拒绝、完成证据和结果未知被准确区分，以免被误导。
18. 作为使用者，我希望超时或结果未知时不自动重试，以避免重复设置或执行操作。
19. 作为使用者，我希望短操作反馈后继续聊天，以减少反复唤醒。
20. 作为使用者，我希望音乐等持续播放开始后豆包让出音箱，以避免回复或监听打断音乐。
21. 作为使用者，我希望再次叫豆包时能恢复原会话，以保留音乐播放前的聊天上下文。
22. 作为使用者，我希望豆包等待讲话时能用“理想同学”切回原生入口，以切换助手。
23. 作为使用者，我希望豆包播报时能以原厂“小爱同学”打断，以保留原生控制入口。
24. 作为使用者，我希望切换助手不重发正在执行的操作，以免产生重复副作用。
25. 作为使用者，我希望所有工具操作及其结果可查询，以便复盘和排查问题。
26. 作为使用者，我希望操作记录在重启后保留到主动删除，以避免容器重建丢失记录。
27. 作为使用者，我希望 Vivi 不可用时能降级到原生音色，以继续获取回复。
28. 作为使用者，我希望普通话输入首先可用，并了解英语、四川话识别的实测效果，以决定是否调整 ASR。
29. 作为使用者，我希望服务器上能验证对话和工具行为而不连接音箱，以便安静地推进开发。
30. 作为使用者，我希望语音合成测试只生成文件而不播放，以免打扰宝宝。
31. 作为维护者，我希望测试 Agent 无权调用生产音箱或生产工具，以防测试产生真实操作。
32. 作为维护者，我希望新功能沿用现有应用生命周期、会话控制与 TTS 路由，以避免形成平行架构。
33. 作为维护者，我希望测试结果区分 Mock、真实模型服务和真实设备证据，以便准确判断交付状态。

## Implementation Decisions

- 以已确认领域词表与“小爱豆包自动播报聊天回复，操作优先委托原生小爱”的 ADR 为产品边界。本功能独立于原生唤醒一期和常驻记录需求，不改变它们的既有完成状态。
- 同一个 Bridge 承载原生与 Hermes 路由，调整当前 `NATIVE_WAKE_ENABLE` 互斥设计。制定明确的模式选择与旧配置迁移规则，保留可验证的纯原生运行路径；不能只删除启动校验后任意混用所有后端。统一命令行、容器、模型准备和启动检查的语义，非法组合在建立设备连接前失败。
- 沿用应用主循环和既有设备状态入口，不建立第二套业务事件循环或全局设备状态。协议接入、会话策略和播放责任分别落在现有边界。
- Hermes profile 使用 `xiaoai-doubao`，展示名“小爱豆包”，一个默认人格和默认会话。Bridge 现有 OpenAI 兼容通道可复用，但其 session 请求头不能被直接当作 Hermes profile 已隔离、工具已授权或聊天历史已持久化的证据。
- 在独立环境验证目标 Hermes 的 profile 选择、工具权限、会话记忆与响应形式。明确一方负责可恢复的聊天上下文，避免客户端历史与服务端记忆重复叠加；提供新会话入口，不依赖当前内存历史实现重启恢复。
- 普通对话每轮得到可朗读文字及声音要求，并经统一 TTS 路由自动播报。具体返回格式通过现有兼容通道的行为验证确定，不预设 Hermes 已支持任意结构化字段或 JSON schema 强制输出。
- 对声音要求进行类型、大小、语种/方言兼容性及音色能力校验。内部元数据、无效结构或工具协议不得直接作为文字朗读。异常返回采取明确的安全回退，不因语音元数据失败重发业务操作。
- 声线默认固定为 `zh_female_vv_uranus_bigtts`。情绪、语种和方言根据上下文动态判断；明确要求优先，单句要求不覆盖原有阶段偏好。偏好只在当前 session 的适用阶段生效，不建立跨 session 长期偏好；新会话不继承旧声音要求。
- 豆包 TTS 2.0 的声音指令使用 `context_texts`，按当前官方协议设置所在位置与编码，列表只使用一条有效指令。语种与方言显式参数按音色能力映射；不把多情感音色的固定情绪枚举当作 Vivi 已支持的全部控制方式。
- 更新 Python 与 Rust 的语音参数传递，覆盖流式和非流式路径，不将语种继续固定为中文。鉴权适配用户实际申请的 TTS 凭据形式，凭据只进入私有运行配置，不写入仓库、提示词或日志。
- Vivi 不可用时允许原生 TTS 降级并记录原因，降级不保证情绪、方言和语种效果一致。在静默环境中，所有降级也必须落到假音箱或文件输出，不得触达真实设备。
- `xiaoai-bridge` skill 统一封装原生命令与播放、打断、唤醒、状态等已需要的控制能力，迁移现有 `xiaoai-tts` 调用和说明。普通回复仍自动播放，不要求模型为每句回复调用播放工具。
- 原生文字指令复用现有 `ask_xiaoai` 能力，经受控接口提交，不向 Agent 开放任意 shell。自然语言参数不能直接拼入未安全转义的 shell 命令；在测试中覆盖引号和特殊字符。
- 豆包发起的操作由 Hermes 反馈，需验证静默提交能否抑制原生播报，并关联原生返回与本次请求。当前布尔返回只证明接口层受理，不能证明业务完成。缺少可读回结果时仅报告已提交但未确认；不承诺能读取全部原生技能的结果。
- 工具操作使用可关联的请求标识。相同请求重复到达不重复执行，超时、进程重启或结果未知不触发自动重放；新的有意请求与重复投递必须区分。
- 操作记录持久化保存时间、session、操作指令、参数、受理情况、实际返回、错误及确认程度。请求发送前后均有可追踪状态，异常中止不伪装为完成；记录保留到主动删除，不记录凭据，不额外录制整段聊天。
- 原生播报、Hermes 回复、持续播放和监听有明确的控制权。短操作完成当前反馈后继续聊天；持续播放由 Hermes 简短反馈后让出音箱并暂停交互，避免后续提示音或采音重启中断音乐。具体先后与可观测结果按动作验证，不先声称音乐已开始。
- 自定义词在豆包等待讲话时可分流或切回；播报时以原厂词打断作为首版目标。切换会取消旧会话的后续反馈或播放任务，不重发已提交操作，不让迟到回复覆盖新会话。自定义词在播报期间可靠打断不属于首版保证。
- 输入识别复用已有 ASR 选择和连续对话入口。优先验证普通话；英语和四川话输入先实测记录，不将稳定识别二者作为首版硬指标。TTS 能说某种语言不代表 ASR 能准确识别。
- 服务器静默环境使用独立项目、容器、网络、凭据、会话和持久化目录。假 Client 只记录协议并返回预设结果，绝不执行收到的设备命令；输出音频保存为文件或被测试接收器消费，不调用播放器。
- 隔离不只依靠一个静音开关或未安装播放软件：测试 Bridge、Agent 与工具均不可访问生产控制端点及真实音箱，不继承生产工具、远端 shell、Docker 管理能力或生产秘密；测试所需模型服务连接与设备控制网络分开配置。
- 缺少真实 Hermes/TTS 凭据时继续 Mock 验证，明确标注尚未覆盖的真实服务项目。真实服务测试只在专用工具权限和网络边界已核验后运行，不能让已配置生产工具的 Agent 处理测试控制语句。

## Testing Decisions

- 已在讨论中确认的主要测试边界是“用户请求到可观察回复、工具行为、操作记录和语音产物”的完整路径。尽量复用现有对话入口、TTS 路由、原生命令传输与假 Client，而非按私有方法逐层镜像测试。
- 本地自动化运行真实应用协调逻辑，替换 Hermes、TTS 网络与设备传输等外部边界。断言用户可观察的文字、声音请求、文件、操作状态及实际传输次数，不把模型内部推理作为测试接口。
- 先以文字输入完成默认人格、默认 session、恢复、新会话、普通自动回复的闭环；再验证逐轮声音控制、阶段偏好与结构异常回退。模型语义判断用真实服务场景单独记录，不将 Mock 固定答案冒充模型判断质量。
- 工具测试覆盖原生命令静默参数、引号传递、受理/拒绝/超时、重复请求、重启后未知状态、日志持久化及凭据脱敏。假的业务成功结果必须明确标为模拟，不能作为真实设备验收。
- 对话协调测试覆盖短操作继续、音乐让出、三入口分流、原厂唤醒中断、迟到回复丢弃、切换不重发、TTS 降级以及失败后的下一轮恢复。
- 声音测试验证普通话、英语、四川话的参数与产物；凭据可用时实际合成为文件，但不播放。文件格式和非空只证明接口产物有效，听感、情绪自然度和方言准确性保留为后续人工试听项目。
- 使用文件音频验证识别输入及“豆包豆包”KWS 词表和路由。既有原生唤醒假 Client 工具可作为先例，但它只支持原生协议，需要扩展对话和播放协议后才能覆盖新功能。
- 复用已有原生模式启动、唤醒分流、OpenAI 兼容通道、TTS 路由和 ASR 测试。记录纯原生回归结果，覆盖旧配置迁移与新混合配置的启动条件。
- 服务器上先验证隔离边界：生产服务未变更、真实 Client 未连接测试服务、测试工具仅可达测试 API；随后跑 Mock 全链路和可用的真实服务测试，保存结果与产物。不得运行可能连接生产设备的现有 live 测试作为默认检查。
- 所有证据区分离线测试、服务器 Mock、真实 Hermes、真实豆包合成与真实音箱。报告跳过、待测和失败项，不将没有凭据的测试计为通过。

## Out of Scope

- 直接接入 HA、调用 HA 工具及配置实体权限。
- 多角色、多家庭成员身份识别和多音色切换。
- 跨 session 的长期声音偏好画像。
- 新建常驻录音、说话人识别、自然日日报或自动摘要。
- 保证原生小爱的所有技能均支持文字调用或均可读回业务完成状态。
- 保证任意语种/方言输入准确、任意语种/方言组合均可合成。
- 保证正在播报时两个自定义词可靠打断、全双工说话或同时保留两个活动助手。
- 当前阶段的真机连接、真实原生命令调用、生产部署/重启、音箱发声和试听验收。
- 自动刷机、设备启动项、SSH 或固件修改。

## Further Notes

设计依据为本次讨论、项目领域词表与第二份 ADR。现有纯原生部署和未提交的其他需求文件不应混入本功能提交或被测试覆盖。

一手 API 依据：豆包 TTS [单向流式合成接口](https://www.volcengine.com/docs/6561/1598757)与[音色表](https://www.volcengine.com/docs/6561/1257544)。音色表与显式方言参数列表的范围存在粒度差异，首版以协议可验证范围和实际结果为准。

原生反馈的静默控制与业务结果获取、Hermes profile/tool 隔离与逐轮声音信息返回，都是需要实现验证的技术契约。未验证前可运行完整 Mock 闭环，不可声称对应真实能力已经可用；无法满足时明确记录限制，不偷换为原生音色回应或重复发令。

首个闭环建议从文字输入到 Hermes 回复与声音要求、测试输出及操作记录开始。后续任务均按能独立验证的行为拆分，最后汇总服务器静默报告；真实设备验收另行获得用户允许后进行。
